# 7. The image and the installer

Roadmap step 7 of the [plan](0%20-%20plan.md#roadmap-option-b): "Image and installer. Use `mkosi` for quick VM/disk images during development. For a bootable installer ISO, use live-build or a Calamares-based ISO. Both tools are choices, not requirements." Started 2026-10-10. The answer in one line: a live ISO on Ubuntu's own live stack (casper), with Ubuntu's own installer package (Calamares, the one Lubuntu and Ubuntu Studio ship) configured for this desktop, booting through Ubuntu's Microsoft-signed shim and Canonical-signed GRUB so that Secure Boot works out of the box, assembled by one script with xorriso; the QEMU boot test runs it under OVMF with Secure Boot on and off. The installed system is verified by hand (section "Verified"), because Calamares has no unattended mode.

## Terms

Terms from earlier documents keep their meaning: [Secure Boot and shim](1%20-%20policy.md#secure-boot-and-shim), [LUKS](1%20-%20policy.md#luks), [Plymouth](1%20-%20policy.md#plymouth), [QEMU and OVMF](1%20-%20policy.md#qemu-and-ovmf), [root filesystem tarball and profile](3%20-%20rootfs.md#terms), [apply-system](6%20-%20omarchy-port.md#apply-system).

### Live medium and casper

A live medium is a DVD or USB stick that boots a complete system from a read-only, compressed copy of a root filesystem (a squashfs) with a writable overlay in RAM on top, so the user can try the desktop and run the installer without touching the disk. casper (stonking `casper 26.10.2`, main) is Ubuntu's live-boot machinery: a set of initramfs-tools scripts that find the squashfs on the medium, mount it with the overlay, create the live user and its autologin, and hand over to systemd. Its scripts read a few kernel command-line parameters, among them `boot=casper` (take the live path at all), `username=` and `hostname=`.

### Squashfs

A compressed, read-only filesystem in a file, made by `mksquashfs` (stonking `squashfs-tools 1:4.7.5-1`). Since squashfs-tools 4.5, `mksquashfs` can read a tar archive on standard input (`-tar`), which lets the ISO build compress the root filesystem tarball directly, with the tar's ownership and permissions and without root.

### Squashfs layers

Several squashfs files that casper stacks into one root filesystem with overlayfs, each upper one holding only what differs from the ones below it: added and changed files, and whiteouts (overlayfs's character devices 0/0) for removed ones. casper's kernel parameter `layerfs-path=<name>` names the top layer, and casper derives the layers below it by dropping the name's last dot-separated part: `layerfs-path=filesystem.live.squashfs` mounts `filesystem.squashfs` and then `filesystem.live.squashfs` above it (`casper` script, `layerfs-path=*` and the "compute list of depending layers" loop, read from the live tarball 2026-10-18). Without the parameter casper stacks every `*.squashfs` in the directory in name order. In the live session casper moves its first squashfs mount, the bottom layer, to `/rofs`.

### EFI System Partition image

UEFI firmware boots from a FAT filesystem that holds `EFI/boot/bootx64.efi`. On an ISO that filesystem is a FAT image file appended to the ISO 9660 image as a GPT partition of type EFI System; xorriso does the appending (`-append_partition 2 0xef <image> -appended_part_as_gpt`). The image is made with `mkfs.vfat` and filled with mtools (`mmd`, `mcopy`), which write into a FAT image file without mounting it.

### Signed boot chain on a live medium

Ubuntu's `shim-signed` ships shim as `/usr/lib/shim/shimx64.efi.signed.latest`, signed by Microsoft, and `grub-efi-amd64-signed` ships two Canonical-signed GRUB images: `grubx64.efi.signed`, built with the prefix `/EFI/ubuntu` for installed systems, and `gcdx64.efi.signed`, the CD variant, built with the prefix `/boot/grub` and an embedded configuration that searches every filesystem for `/.disk/info` and takes `/boot/grub` on that medium as its prefix (grub2's `debian/build-efi-images`). A live medium therefore carries shim as `bootx64.efi`, `gcdx64.efi.signed` as `grubx64.efi` beside it, MokManager (`mmx64.efi`), a `/.disk/info` file at the root of the ISO, and its menu at `/boot/grub/grub.cfg`.

### Calamares

A distribution-independent graphical installer framework (stonking `calamares 3.3.14-0ubuntu30`, universe, with `calamares-data`). A distribution gives it a settings file naming the sequence of modules to show (pages) and to run (jobs), one configuration file per module, and a branding directory. Ubuntu's package ships the program and the modules but no module configuration at all (its `/etc/calamares` is empty; the schemas under `/usr/lib/x86_64-linux-gnu/calamares/modules/` are for validation), so a flavour ships a settings package: Lubuntu's is `calamares-settings-lubuntu 1:26.10.7` with `calamares-settings-ubuntu-common`, the reference this document's configuration follows where it is Ubuntu-specific.

### KPMcore

The KDE Partition Manager core library (stonking `kpmcore 26.08.1-0ubuntu2`, universe; binary package `libkpmcore13`), which [Calamares](#calamares)'s partition module drives for every disk operation: KPMcore runs `sfdisk` to write partition tables, `mkfs` for filesystems and `cryptsetup luksFormat` for encrypted volumes, each through its root helper over D-Bus, and reports each command in the installer's job details. Since 26.08 (upstream commit 25d3a793, 2026-02-09) KPMcore's LUKS2 format command carries `--sector-size 4096`; Ubuntu's `26.08.1-0ubuntu2` (2026-10-12, LP: #2170640) lowers it to 512.

### Alternatives (update-alternatives)

Debian's mechanism for several packages providing one path: each registers a candidate with a priority and `update-alternatives` keeps a symlink at the shared path pointing at the highest priority, or at the administrator's choice. Ubuntu's Plymouth theme packages register `/usr/share/plymouth/themes/default.plymouth` this way (`plymouth-theme-spinner` registers `bgrt` at priority 110), and Plymouth's initramfs hook copies whatever that link points at into the initramfs.

### DMI strings (SMBIOS)

The firmware's description of the machine, in its SMBIOS tables (the System Management BIOS standard); Linux shows the fields as files under `/sys/class/dmi/id/`. This laptop, read on 2026-10-13: `sys_vendor` is `LENOVO`, and `product_version` (where Lenovo puts the model name) is `Legion Pro 7 16IAX10H`. QEMU sets the same fields with `-smbios type=1,manufacturer=...,version=...`.

## Anatomy

`make iso` runs `scripts/iso-create.sh`. The command's inputs are two profiles of the root filesystem tarball from the same build: the desktop profile, `build/rootfs/oaxaca-26.10-amd64-desktop.tar` from `make rootfs PROFILE=desktop`, which is the system an installation puts on the disk, and the live profile, `build/rootfs/oaxaca-26.10-amd64-live.tar` from `make rootfs PROFILE=live`: the desktop profile's packages plus `oaxaca-live` and `oaxaca-installer`, with the initramfs rebuilt at the end of the mmdebstrap run so that casper's scripts, installed in the same run as the kernel, are in it. The script stops when a package both tarballs have differs in version. It writes `build/iso/oaxaca-26.10-amd64.iso` from these parts:

1. `casper/filesystem.squashfs`: the desktop tarball, compressed by `mksquashfs -tar` (zstd, level 15), with `casper/filesystem.manifest` and `filesystem.size` beside it, as casper's conventions expect. Above it, `casper/filesystem.live.squashfs`: the [squashfs layer](#squashfs-layers) holding what the live tarball has on top of the desktop one, written by `scripts/layer-diff.py`, with `casper/filesystem.live.manifest` (choice 55).
2. `casper/vmlinuz` and `casper/initrd`: the newest kernel and its initramfs, extracted from the live tarball.
3. `boot/grub/grub.cfg`: two entries, "Try or install" with `boot=casper layerfs-path=filesystem.live.squashfs username=oaxaca hostname=oaxaca quiet splash`, and a safe-graphics one adding `nomodeset`. `/.disk/info` names the distro, version, series and build date; the CD GRUB finds the medium by that file.
4. `efi.img`: a FAT image with `EFI/boot/bootx64.efi` (shim), `EFI/boot/grubx64.efi` (the CD GRUB) and `EFI/boot/mmx64.efi` (MokManager), all three extracted from the tarball's own `shim-signed` and `grub-efi-amd64-signed`.
5. `pool/`: the NVIDIA driver's packages for the tarball's kernel with a flat `Packages` index and the license (`LICENSE.NVIDIA`), written by `scripts/driver-pool.sh`, so the installer's drivers step works offline (choice 20, 2026-10-11); also the hardware packages (choice 41) and the root filesystem tools the filesystem step adds (`btrfs-progs`, `timeshift`, `xfsprogs`, choice 55), each with its dependencies, resolved against the desktop tarball. `md5sum.txt` at the root covers every file above.

xorriso writes the ISO 9660 image (Rock Ridge and Joliet, level 3) with `efi.img` appended as the EFI System partition, bootable through El Torito's EFI entry. The same xorriso then copies that ISO to `oaxaca-26.10-amd64-test.iso`, replacing only `/boot/grub/grub.cfg` with a version whose default entry has `console=ttyS0`, `systemd.mask=serial-getty@ttyS0.service` and `oaxaca.boottest`, and no timeout; the squashfs is compressed once.

On the medium, boot goes: firmware, shim (Microsoft's signature), `grubx64.efi` (Canonical's signature, checked by shim), the kernel (Canonical's signature, checked by GRUB through shim), casper's initramfs scripts (squashfs found under `/cdrom/casper`, overlay mounted, live user `oaxaca` created with passwordless sudo through `/etc/sudoers.d/casper`, `[Autologin]` appended to `/etc/sddm.conf`), then systemd and SDDM. `oaxaca-live`'s casper-bottom script `16oaxaca_autologin` runs right after casper's `15autologin` and fills in the session name casper leaves empty (casper knows only Kubuntu's, Plasma's, Lubuntu's and Budgie's session files), so SDDM logs the live user into the desktop's own session. In that session, `/etc/xdg/autostart/oaxaca-installer.desktop` (from `oaxaca-installer`) starts the installer through uwsm's autostart handling; the launcher `oaxaca-installer` runs `sudo -E calamares -D8` with `QT_QPA_PLATFORM=wayland`.

`make iso-test` runs `scripts/iso-boot-test.sh`: QEMU with OVMF (`OVMF_CODE_4M.secboot.fd` with a copy of `OVMF_VARS_4M.ms.fd`, Microsoft's keys enrolled, for `SECURE_BOOT=on`; the same firmware with `OVMF_VARS_4M.fd`, no keys, for `off`, which the guest's `mokutil` reports as "SecureBoot disabled"; the plain `OVMF_CODE_4M.fd` has no Secure Boot support compiled in and reports "This system doesn't support Secure Boot", a different case from a machine with the setting off), the test ISO as a CD, a virtio GPU with virgl when the host's render node is writable, the serial console logged to a file. In the guest, `oaxaca-live`'s `oaxaca-live-boot-test.timer` and service, which exist only when the kernel command line carries `oaxaca.boottest`, wait for the session and print one line per check, then power off; the host script compares the lines.

## Installing: what Calamares does, in order

`oaxaca-installer` ships `/etc/calamares/settings.conf`, one file per module under `/etc/calamares/modules/`, and `/etc/calamares/branding/oaxaca/`. The pages shown: welcome (requirements: 20 GB of disk, 4 GB of RAM, root; network and power reported but not required), locale, keyboard, partition, users, summary. The jobs run, with each one's configuration:

| Job | What it does here | Configuration |
|---|---|---|
| `partition` | GPT, a 512 MB EFI System Partition at `/boot/efi`, btrfs by default since choice 52 (ext4 and xfs offered), optional LUKS2 encryption with a separate unencrypted 4 GB `/boot`, swap file by default or none | `partition.conf`, after Lubuntu's |
| `mount`, `unpackfs` | mounts the target; copies `/cdrom/casper/filesystem.squashfs`, the installed system's layer, whole (the live layer above it stays on the medium, choice 55) | upstream `mount.conf`; `unpackfs.conf` |
| `machineid`, `fstab`, `locale`, `keyboard`, `localecfg` | the installed system's identity, `/etc/fstab` and `/etc/crypttab`, locale and keyboard | upstream defaults |
| `luksbootkeyfile`, `luksopenswaphookcfg`, `initramfscfg` | with encryption: a key file so the passphrase is asked once, and the initramfs-tools hook that carries it | upstream defaults; `initramfscfg` has none |
| `users` | the first user, in `adm cdrom dip lpadmin plugdev sudo`, password of 8 characters or more, no root password, no autologin | `users.conf` |
| `displaymanager` | SDDM, the user's session `oaxaca` through uwsm; the session package's own SDDM configuration is left alone (`basicSetup: false`) | `displaymanager.conf` |
| `networkcfg`, `hwclock`, `services-systemd` | the live session's network connections carried over, the hardware clock, no unit changes | upstream defaults |
| `shellprocess@filesystem` | `/usr/libexec/oaxaca/filesystem-setup <target>` from the live system: installs the root filesystem's tools from the medium's pool, `btrfs-progs` and Timeshift with `/etc/timeshift/timeshift.json` on btrfs, `xfsprogs` on xfs; on ext4, nothing (choices 51 and 55) | `shellprocess_filesystem.conf` |
| `shellprocess@system` | `apt-get -q update` (non-fatal), then `oaxaca-apply-system --install-user <user> --first-install` in the target: the desktop's install-time setup (step 6), with the user name from the users page | `shellprocess_system.conf` |
| `shellprocess@drivers` | `oaxaca-drivers-install` in the target (step 4): the NVIDIA driver branch with prebuilt signed modules when the machine has an NVIDIA GPU; a failure does not abort | `shellprocess_drivers.conf` |
| `shellprocess@hardware` | `/usr/libexec/oaxaca/hardware-install <target>` from the live system: the hardware package for the machine's model, from the firmware's [DMI strings](#dmi-strings-smbios) (`oaxaca-hw-legion` on the Lenovo Legion Pro 7 16IAX10H), from the medium's package pool; a failure does not abort | `shellprocess_hardware.conf` (choice 41) |
| `grubcfg`, `bootloader` | `/etc/default/grub` with `quiet splash`; `grub-install` for EFI, which on Ubuntu installs shim and the signed GRUB under `/boot/efi/EFI/ubuntu` | `grubcfg.conf`, `bootloader.conf` |
| `initramfs` | `update-initramfs -u -k all` in the target, after the key hook and the boot loader are in place | `initramfs.conf` |
| `shellprocess@factory` | `/usr/libexec/oaxaca/factory-snapshot <target>` from the live system: on a btrfs root, the read-only `@factory` snapshot of `@` that the factory reset returns to, with a copy of a separate `/boot` inside it; on any other filesystem, nothing (choice 52) | `shellprocess_factory.conf` |
| `umount` | unmounts the target; `finished` offers the reboot | upstream default; `finished.conf` |

Two names in that table are fixed by Ubuntu's signed images, not chosen here: the EFI directory `ubuntu` (choice 3) and the boot loader entry name in `branding.desc` that goes with it.

## Plymouth

The desktop's Plymouth theme files have been in `oaxaca-config` since step 6 (`/usr/share/plymouth/themes/oaxaca/`), and `plymouth` joined the package list in this step. The theme is turned on the way Ubuntu's own theme packages do it: `oaxaca-config`'s postinst registers `/usr/share/plymouth/themes/oaxaca/oaxaca.plymouth` as the `default.plymouth` alternative at priority 150, above `plymouth-theme-spinner`'s 110, and runs `update-initramfs -u` so the theme reaches the boot splash; its prerm removes the registration. `oaxaca-plymouth-set`, which on Arch called `plymouth-set-default-theme`, a program stonking does not ship, now runs `update-alternatives --set default.plymouth` on that path before its `update-initramfs -u`. This closes the item step 6 left for step 7.

## Choices

1. **Ubuntu's live stack and Ubuntu's installer package, not live-build, not mkosi, not Omarchy's installer.** casper is what every Ubuntu flavour's live ISO boots with, and Calamares is in Ubuntu's archive with the settings of two official flavours as a worked example; both are "Ubuntu's own" in the sense of step 6's rule. Ubuntu's flagship installer (`ubuntu-desktop-bootstrap` with Subiquity) is not a deb in stonking (checked on Launchpad: neither name is published), exists only as a snap, and is built around livecd-rootfs's layered squashfs, so it would mean adopting livecd-rootfs whole. Rejected: live-build (Debian's tool; its live-boot is not casper, and Ubuntu's flavours do not use it); mkosi (makes disk images, not a casper live ISO; the root filesystem tarball with the QEMU boot test already covers the "quick VM image" role the plan gave it); porting Omarchy's own ISO installer (Arch's live medium and an Arch-specific orchestrator).
2. **One script with xorriso, not livecd-rootfs.** livecd-rootfs is Ubuntu's own image builder, but it is written for Launchpad's build farm, drives live-build, and assembles a layered set of squashfs images for Subiquity; for one squashfs on casper, the layout is small enough to write down: the four parts in "Anatomy". The script is 120 lines and every part is a file the QEMU boot test either boots or reads. Rejected: livecd-rootfs; `grub-mkrescue` (writes an unsigned GRUB of its own, so the ISO would not boot with Secure Boot on).
3. **The EFI directory is `ubuntu`, and the live medium uses the CD GRUB image.** *Corrected by choice 56 (2026-10-20): the directory is `ubuntu` only for the installer's `grub-install`; GRUB and shim updates install into `EFI/oaxaca` (from the source, not observed on the laptop).* Ubuntu's `grubx64.efi.signed` is built with the prefix `/EFI/ubuntu` (grub2's `debian/build-efi-images`: `-p /EFI/$efi_vendor`), so it reads its configuration stub from `/boot/efi/EFI/ubuntu/grub.cfg` and nowhere else; Calamares's `efiBootloaderId` is therefore `ubuntu`, which Calamares's own `bootloader.conf` recommends for Debian derivatives in the same words for `debian`. On the medium, `gcdx64.efi.signed` is the image built for exactly this use, with `/boot/grub` as its prefix and an embedded search for `/.disk/info`, so the ISO needs no configuration stub on the EFI partition at all. Rejected: a directory named after the distro (the signed image would not find its configuration; an unsigned GRUB with our prefix would break Secure Boot).
4. **UEFI only.** The policy's hardware is UEFI, Secure Boot is the requirement the boot chain is built for, and a BIOS boot record would add GRUB's unsigned `eltorito.img` and a second code path the test does not exercise. Rejected: a hybrid BIOS and UEFI image, which Ubuntu's own ISOs still write; revisit if a BIOS-only machine turns up.
5. **The installer autostarts in the live session, and also sits in the application list.** The live user lands on the desktop with the installer open, the way Ubuntu's own live session behaves; closing it leaves a working desktop and the launcher under System. Rejected: a live session without the installer open (a user who booted the medium to install would look for it).
6. **The ISO boot test checks the live session and the installer's presence; the installation itself is verified by hand.** Calamares has no unattended or scripted mode (its documented command-line options are the debug level, the configuration directory and the branding; nothing fills the pages), and driving its Qt window from a script inside a Wayland session would be a test of the automation, not of the installer. What the automated test proves: the signed chain boots with Secure Boot on, casper's live session comes up in the desktop with the shell, and the installer starts with its window on screen reading this package's configuration. What the hand-run installation proves is listed under "Verified", and the checklist is the plan's verification list. Rejected: an unattended install driven by `ydotool` (brittle, and a failure would not say whether the installer or the automation broke); a second, scripted installer only for tests (two installers to keep consistent).
7. **The test variant of the ISO is a second file made by xorriso from the first.** The guest's test unit must be woken by the kernel command line, which lives in `grub.cfg` on the medium; GRUB offers no way to pick an entry from the host, and keystrokes into QEMU at the right moment are timing. Copying the ISO and replacing one file takes seconds, while compressing the squashfs twice takes minutes. Rejected: two full builds; a GRUB entry chosen by sending keys through QEMU's monitor.
8. **Swap file by default, hibernation out.** The policy keeps hibernation out of the first release in every configuration, so the partition page offers a swap file or no swap, never a swap partition sized for hibernation; a user who needs none picks none. Rejected: a swap partition (would only matter for hibernation).
9. **A separate unencrypted `/boot` when the user chooses encryption.** Ubuntu's GRUB does not unlock LUKS2 on its own, and this is Lubuntu's layout for the same reason: a 4 GB ext4 `/boot` outside the encrypted volume, present only when encryption is chosen (`onlyPresentWithEncryption`). Rejected: `/boot` inside the LUKS volume (needs LUKS1 or a GRUB with the LUKS2 module and a second passphrase prompt).
10. **The default root filesystem profile is the newest layer, now `live`.** `make rootfs`, `make rootfs-test` and `make drivers-check` take `PROFILE`, and the Makefile's default moved from `desktop` to `live` on 2026-10-11, so that on a fresh clone the plain targets produce and test the tarball the ISO is made from, with no profile to remember. The boot test treats `live` as `desktop`: the live tarball adds only casper, `oaxaca-live` and `oaxaca-installer`, so the desktop checks apply. Two parts of those packages do act when the tarball boots from a disk instead of the ISO, and the first run showed both: `casper-md5check.service` failed (the unit verifies `/cdrom/md5sum.txt`, which only the ISO carries, and has no condition on the kernel command line), and the installer's autostart entry ran `sudo calamares` and died on the password prompt. The test's image preparation masks that unit and removes that entry for the live tarball; the ISO test is where both are exercised. The run after that fix is in Verified below. Rejected: keeping `desktop` as the default and naming `live` only in the ISO step, which left `make rootfs` producing a tarball `make iso` refuses.
11. **KPMcore rebuilt from Ubuntu's source package with one patch, so an encrypted install works in every partitioning mode (2026-10-11).** *Dropped 2026-10-14: Ubuntu's `kpmcore 26.08.1-0ubuntu2` (2026-10-12, "Reduce LUKS2 cryptsetup sector size to 512", LP: #2170640) fixes the same refusal by forcing 512-byte sectors, and outranked our `26.08.1-0ubuntu1oaxaca1`, so installed systems would have upgraded to it anyway. The image now carries Ubuntu's. The cost against our patch: 512-byte encryption sectors even on drives with 4K physical sectors, where our patch let cryptsetup pick 4096.* The first hand-run install, on the Legion laptop with encryption, with the root volume as the fifth partition of its 1 TB NVMe drive, ended in "The installer failed to create partition on disk", and the last command in the job's details was `cryptsetup --use-random --sector-size 4096 --key-size 512 --hash sha512 --batch-mode --force-password --type luks2 luksFormat /dev/nvme0n1p5`. The cause has three parts. [KPMcore](#kpmcore) 26.08 forces 4096-byte encryption sectors. cryptsetup refuses that option on a partition whose size in bytes is not a multiple of 4096: "Device size is not aligned to requested sector size", reproduced on this workstation with KPMcore's exact command on a 64 MiB plus 512 byte image file (exit 1), while the same command on a 64 MiB file succeeds. And Calamares 3.3.14 aligns the partition it creates only for "Erase disk": Ubuntu's `align-end-sector-to-4k.patch` (`calamares 3.3.14-0ubuntu29`, Launchpad bug 2165428, reported against Kubuntu stonking on 2026-08-27; the live image's 0ubuntu30 carries it) touches `doAutopartition` alone, while "Replace a partition" keeps the old partition's exact first and last sector (`doReplacePartition`) and "Install alongside" starts the new partition two sectors past where the size slider landed (`ChoicePage::doAlongsideApply`), both in Calamares 3.3.14's source. Upstream Calamares fixed "Erase disk" in 3.4.0 (issue 2480, pull request 2490, merged 2026-03-07), removed the alignment from "Replace" on purpose ("Do not change sectors when replacing a partition", 2026-03-08) and has manual partitioning open (issue 2526). The fix here is `packages/kpmcore`: Ubuntu's `kpmcore 26.08.1-0ubuntu1` rebuilt as `26.08.1-0ubuntu1oaxaca1` with one patch, `luks2-no-forced-sector-size.patch`, which drops `--sector-size 4096`, so that cryptsetup chooses the sector size itself: cryptsetup's LUKS2 format code (`lib/setup.c`, read at 2.8.4) takes 4096 when the drive reports 4K physical sectors and the device size allows it, and otherwise logs "Device size is not aligned to sector size. Reverting to 512 bytes." `scripts/build.sh` gained a fourth way of naming a source, `DSC=`: the package directory holds the patch, its series line and one changelog entry, laid over Ubuntu's `debian/` after `dpkg-source -x`, so there is no fork of KPMcore and no copy of Ubuntu's packaging in this repository. Only `libkpmcore13` goes into the live profile (`scripts/rootfs-create.sh`); the installer's package removal (`packages.conf`, `try_remove` of `calamares`) leaves the library on the installed system, where Ubuntu's next upload replaces it, since `26.08.1-0ubuntu2` and `26.08.2-0ubuntu1` both sort above `26.08.1-0ubuntu1oaxaca1`. Rejected: rebuilding Calamares with an alignment patch for "Replace" and "Alongside" (the larger build, manual partitioning still open upstream, and against upstream's decision for "Replace"); offering encryption only with "Erase disk", the one mode that works on the unpatched image (not this laptop's layout, with four partitions before the root); waiting for Ubuntu (no report covers the two modes as of 2026-10-11; the report is in the developer README's [To do](README.md#to-do)).
12. **The installer package depends on the programs Calamares's modules run, starting with rsync (2026-10-11).** The second install on the Legion laptop got through partitioning (choice 11 held) and failed in the next job: "Failed to unpack image /cdrom/casper/filesystem.squashfs", "rsync failed with error code 127", the shell's code for a command that is not there. Calamares 3.3.14's `unpackfs` module always copies with `rsync -aHAXSr` (its `main.py` builds an `UnpackOperation` for every entry; the `unsquashfs` path exists in the file but `run()` never takes it), and Ubuntu's `calamares` package depends on `os-prober` and `util-linux-extra` only, recommending `btrfs-progs` and `squashfs-tools`: Ubuntu's own images get rsync from the standard task, which this minbase image never installs, and the base image turns recommends off. `oaxaca-installer 0.1.1` depends on `rsync`, and on `btrfs-progs` and `xfsprogs` because the partition page offers btrfs and xfs and their `mkfs` tools were missing the same way. The ISO boot test now prints `installer tools missing: [...]` for the twelve programs the sequence runs and fails unless the list is empty. Rejected: switching the module to its unsquashfs routine (not reachable from the configuration in 3.3.14); depending on Ubuntu's `calamares-settings-ubuntu-common` for its dependency list (it does not name rsync either).
13. **The medium carries `md5sum.txt`, so casper's integrity check runs instead of failing (2026-10-11).** The laptop's boot log showed `Failed to start casper-md5check.service`: the unit runs `casper-md5check /cdrom /cdrom/md5sum.txt` after `multi-user.target`, and the ISO had no such file. `scripts/iso-create.sh` now writes one at the root of the medium, one `<md5>  ./path` line per file (the layout of Ubuntu's ISOs), and gives the test image its own copy naming the test `grub.cfg`. The ISO boot test prints `failed units: [...]` and fails unless the list is empty.     Now `scripts/iso-create.sh` builds the ISO from the desktop tarball and the live tarball of the same build. `casper/filesystem.squashfs` is the desktop tarball, the installed system. `casper/filesystem.live.squashfs` is a [squashfs layer](#squashfs-layers) with what the live tarball has on top of it, computed by `scripts/layer-diff.py`: entries that are new or differ in type, mode, owner, link target, device numbers, extended attributes or content (SHA-256, modification times ignored since the two tarballs come from separate mmdebstrap runs), whiteouts for entries the live tarball lacks, every parent directory of those with the live tarball's attributes, and every name of a hard-linked file when one of its names is in the layer. Installs by 0.1.11 started with an empty `/var/lib/apt/lists`, and Install > AI > Dictation failed with "Unable to locate package voxtype" until the first update. `shellprocess@system` now runs `apt-get -q update` in the target first, non-fatal so an install without a network still finishes; `oaxaca-pkg-add`, which the menu's Install entries use, fetches the lists itself when there are none; and `tests/factory-reset/run.sh` repeats the update, with the factory reset test checking `factory install: apt lists:` above zero.*

    The desktop layer has no `btrfs-progs`, `xfsprogs` or Timeshift; the live packages brought them before (choice 51). `snapshots-setup` is now `filesystem-setup`, run as `shellprocess@filesystem` in the same place: on btrfs it installs `btrfs-progs` and `timeshift` and writes Timeshift's configuration, on xfs it installs `xfsprogs`, on ext4 nothing (`e2fsprogs` is in every system). It installs from the medium's pool, to which `scripts/driver-pool.sh` adds the three packages with their dependencies, resolved against the desktop tarball rather than the live one, since the pool serves the installed system. It runs before the `initramfs` step, so the target's initramfs gets the btrfs and xfs hooks those packages carry. `make release` builds `make rootfs PROFILE=desktop` before `make rootfs`. `iso-create.sh` stops when a package both tarballs have differs in version, a sign that the desktop tarball is left over from an older build; a package only one has is allowed, since with the live packages in the same install apt satisfies `plymouth`'s theme dependency with `plymouth-theme-hamara` instead of the desktop's `plymouth-theme-ubuntu-text`.

    Tests: `live-boot-test` prints `live packages: installed layer 0 live view 4` (the four of `casper`, `calamares`, `oaxaca-live` and `oaxaca-installer` counted in `/rofs`'s and the running system's dpkg databases), and its check on installer steps that run inside the target now flags any program whose package is not in `casper/filesystem.manifest`; `tests/factory-reset/run.sh` unpacks `filesystem.squashfs` and runs `filesystem-setup` in place of the removal; `tests/iso-drive/hardware` copies `/rofs`. Not changed: `calamares`'s third patch (choice 54) stays, since the message it fixes is Calamares's own; no Oaxaca step shows it now. Rejected: two complete squashfs files, the desktop one for the installer and the live one for the session (a second copy of the desktop on the medium); building the lower layer by removing the live packages from a copy of the live tree at build time (installing and then stripping, only earlier); a single mmdebstrap run that saves the desktop tree with a `tar-out` hook before installing the live packages (the hook runs before mmdebstrap's cleanup and with the chroot's `/dev`, `/proc` and `/sys` mounted, so the saved tree would need its own cleanup, and the run's later hooks replace the apt sources the live packages install from).

56. **Two Oaxaca installs on the Legion laptop, one per disk, the daily one labeled "Stable Oaxaca" (2026-10-20).** The maintainer: "I need a way to continue working on Oaxaca while using it as my daily driver." The plan replaces choice 50's Kubuntu and Oaxaca with two Oaxaca installs, each on its own disk with its own EFI System Partition:

    - **Stable Oaxaca**, the maintainer's daily system and the workstation that builds Oaxaca.
    - **The test install**, which the installer's "Erase disk" replaces whenever a new ISO is tested.

    No package changes. Stable Oaxaca needs a one-time step, because otherwise both installs would label their firmware boot entries `Oaxaca`. The firmware entries were checked in Ubuntu's GRUB source (branch `applied/ubuntu/stonking`, commit `05718ae`):

    - **The label.** `grub-install` labels its entry with `GRUB_DISTRIBUTOR` (`efi_title`, `util/grub-install.c`, line 1288). On every run it also reuses or deletes the entries whose label is `efi_title` or the bootloader ID, ignoring case (`strcasecmp`, `grub-core/osdep/unix/efivar.c`, line 622), on any EFI System Partition except those listed in `_UBUNTU_ALTERNATIVE_ESPS`.
    - **The bootloader ID.** GRUB and shim updates run `grub-install` with no `--bootloader-id`: the postinsts of `shim-signed` and `grub-efi-amd64-signed` call `/usr/lib/grub/grub-multi-install --target=x86_64-efi`. `grub-install` then takes the bootloader ID from the first word of `GRUB_DISTRIBUTOR`, in lowercase (lines 1019 to 1027).
    - **Why "Oaxaca daily" fails.** With a label whose first word is `Oaxaca`, the bootloader ID is `oaxaca`, which matches the test install's `Oaxaca` entry, so every GRUB update on the daily system would take over the test install's entry.
    - **The one-time step.** Stable Oaxaca gets `/etc/default/grub.d/90-stable.cfg` with `GRUB_DISTRIBUTOR="Stable Oaxaca"`, then one `grub-install --target=x86_64-efi --efi-directory=/boot/efi` and one `update-grub`. Both `grub-install` and `grub-mkconfig` read `/etc/default/grub.d/*.cfg` after `/etc/default/grub` (`grub-core/osdep/unix/config.c`), so this value wins over the `'Oaxaca'` that the installer's grubcfg step wrote.
    - **Which labels each install takes over.** Stable Oaxaca: `Stable Oaxaca` and `stable`. The test install: `Oaxaca` and `ubuntu` at installation (`--bootloader-id=ubuntu`, choice 3), and `Oaxaca` and `oaxaca` at its updates. No label is on both lists.
    - **Where Stable Oaxaca's loader lives.** Stable Oaxaca's shim and GRUB live in `EFI/stable`. The signed GRUB still reads `/EFI/ubuntu/grub.cfg` (choice 3) from the same EFI System Partition, the stub the installer wrote, which names Stable Oaxaca's `/boot`. That stub must stay.
    - **Boot order.** Every `grub-install` moves its entry to the front of `BootOrder`: `remove_from_boot_order` for the reused entry, then `add_to_boot_order` puts the entry first (`efivar.c`, lines 272 to 317) when no alternative EFI System Partition is listed. Each test reinstall, and each GRUB or shim update on either install, therefore makes that install the default. The maintainer picks the system in the firmware's boot menu, or resets the order with `efibootmgr -o` from Stable Oaxaca.

    **The order of the move.**

    1. Kubuntu's entry is labeled `Kubuntu` first, because the installer's `grub-install --bootloader-id=ubuntu` takes over any entry labeled `ubuntu`.
    2. Stable Oaxaca goes on today's data disk, with "Erase disk", while Kubuntu stays.
    3. After Stable Oaxaca has built Oaxaca, the test install goes on Kubuntu's disk, which removes Kubuntu.

    The two disks are the same model and size, and both carry `oaxaca_boot` and `oaxaca_root` partitions. In the installer, the disk is therefore told apart by serial number (`lsblk -d -o NAME,SERIAL`).

    **Corrections found on the way:**

    - **The fallback loader.** Choice 21's "Ubuntu's own grub-install writes `EFI/BOOT` only with `--force-extra-removable`" is wrong for stonking's GRUB. `grub-install` calls `also_install_removable`, which copies shim, `fbx64.efi` and `mmx64.efi` into `EFI/BOOT` (`util/grub-install.c`, lines 907 to 985), unless it runs with `--no-extra-removable`. The postinst passes that option only when debconf's `grub2/no_efi_extra_removable` is true. `installEFIFallback: false` stops only Calamares's own copy. On the laptop, `EFI/BOOT/BOOTX64.EFI` and `fbx64.efi` on Kubuntu's EFI System Partition carry the same time as the 2026-10-19 install's `EFI/ubuntu` files (Oct 19 19:58).
    - **The EFI directory.** Choice 3's EFI directory `ubuntu` holds only for the installer's `grub-install`. By the bootloader ID rule above, the first GRUB or shim update on an Oaxaca install copies shim and GRUB into `EFI/oaxaca` and points the `Oaxaca` entry there. Boot keeps working because the signed GRUB still reads `/EFI/ubuntu/grub.cfg`. This comes from the source and was not observed on the laptop.

    **Open.** Kubuntu's entry went from `Kubuntu` back to `ubuntu` after Oaxaca installs (read with `efibootmgr` on 2026-10-13 at 05:12, then at 15:10 after one install, and again on 2026-10-16, 2026-10-18 and 2026-10-20). Nothing in this repository or the fork runs `efibootmgr`, Calamares's `grub` bootloader path only runs `grub-install`, and `grub-install` writes `GRUB_DISTRIBUTOR` as the label. Two causes remain:

    - shim's fallback loader recreating the entry from a `BOOTX64.CSV` file (shim-signed's own `/usr/lib/shim/BOOTX64.CSV` reads `shimx64.efi,ubuntu,,This is the boot entry for ubuntu`);
    - the firmware.

    Neither is confirmed. If Stable Oaxaca's entry were ever relabeled `ubuntu`, the next test install would take that entry over. The label is checked before every test install. *Answered by choice 57 (2026-10-23): the firmware.*

    Rejected: the label "Oaxaca daily" (above); an installer option for the label (a new installer page for one machine, used once, and the test install should boot as any user's does); relabeling the test install instead (needed again at every reinstall).

61. **AWS WAF on every CloudFront distribution, each with its own web ACL, and CloudFront's Free flat-rate plan for each (2026-10-24).** Asked for by the distro's maintainer for the three distributions: the apt repository (`apt.oaxaca.page`), the ISO downloads (`get.oaxaca.page`) and the website (`oaxaca.page`, in the `santisbon/oaxaca-web` repository). One web ACL may serve several CloudFront distributions (AWS WAF developer guide, "Associating or disassociating protection with an AWS resource": "You can associate a protection pack (web ACL) with one or more CloudFront distributions", and each distribution with only one), but the maintainer chose CloudFront's flat-rate pricing plans, which include WAF and DDoS protection and charge "no overage charges, regardless of traffic spikes or attacks" (CloudFront developer guide, "CloudFront flat-rate pricing plans", read 2026-10-24). A plan requires a web ACL on its distribution, and whether three plans may share one is not documented, so each distribution has its own: a `WebACL` resource in each distribution's template (`infra/apt-repo/apt-repo.yaml`, `infra/iso/iso-host.yaml`, and the website's `infra/site.yaml`), attached through the distribution's `WebACLId`. A rate-based rule counts requests, not bytes, so WAF alone does not cap the ISO's data transfer; the plan's lack of overage charges does. Subscribing a distribution to a plan is done in the CloudFront console: the aws-cli 2.35.21 snap, the newest on 2026-10-24, has no command for the plans. Rejected: one shared pay-as-you-go web ACL (about $9 a month plus $0.60 per million requests, and no cap on data transfer costs); AWS's managed core rule set (aimed at dynamic sites, and the likeliest to block apt and download tools); Bot Control (would block apt, curl and wget, and is not in the Free plan).

## Running it

```
make build PKG=packages/live             # oaxaca-live
make build PKG=packages/installer        # oaxaca-installer
make build PKG=packages/desktop          # oaxaca-config now registers the Plymouth theme
make rootfs                              # the live tarball (the default profile since step 7): desktop + casper + live + installer, initramfs rebuilt
make iso                                 # build/iso/oaxaca-26.10-amd64.iso and -test.iso
make iso-test                            # QEMU + OVMF, Secure Boot on
make iso-test SECURE_BOOT=off            # the same with Secure Boot off
```

Writing the ISO to a USB stick is a raw copy of the image file to the stick's device, because xorriso wrote the image as a disk: a protective MBR and a GPT with the ISO 9660 filesystem as partition 1 and the EFI System Partition image as partition 2 (`fdisk -l` on the built image, 2026-10-10, trimmed):

```
Disklabel type: gpt
Device   Start      End  Sectors Size Type
...iso1     64  4133711  4133648   2G Microsoft basic data
...iso2 4133712 4145999    12288   6M EFI System
```

The copy itself, with the device found from `lsblk -d -o NAME,SIZE,MODEL,TRAN`, is `sudo dd if=build/iso/oaxaca-26.10-amd64.iso of=/dev/sdX bs=4M status=progress conv=fsync`; the developer README's [Building the distro from source](README.md#building-the-distro-from-source) section has the whole chain in order. Installing by hand: boot the stick, follow the pages, reboot into SDDM, log in; the plan's verification list is the checklist. After an install on a machine with an NVIDIA GPU, check that NVIDIA's driver, not nouveau, holds it, since the installer runs the drivers step as "may fail" (choice 36):

```
basename "$(readlink /sys/bus/pci/devices/0000:02:00.0/driver)"   # nvidia (02:00.0: the GPU's address in lspci)
lsmod | grep -c '^nvidia'                                          # above 0
cat /var/log/oaxaca/drivers-install.log                            # driver: nvidia:<branch>-open ...
cat /var/log/oaxaca/hardware-install.log                           # package: oaxaca-hw-legion; pool: /cdrom/pool
lsinitramfs /boot/initrd.img-"$(uname -r)" | grep -cE '/nvidia(-drm|-modeset|-uvm|-peermem)?\.ko'  # 0 on hybrid graphics (choice 39)
```

`oaxaca-debug-launch` prints the same as `bound:` on its `nvidia driver:` line. On a machine that shares its EFI System Partition with another Ubuntu-family system, also check that the shared stub starts with `# Written by oaxaca-loader-fallback` and that `/var/log/oaxaca/keep-previous-loader.log` names the other system (choices 37 and 38).
