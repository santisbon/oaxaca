# 6. The Omarchy port

Roadmap step 6 of the [plan](0%20-%20plan.md#roadmap-option-b): "port Omarchy into packages (fork omacom/omarchy; MIT, keep the license)". Done 2026-10-10. The answer in one line: Omarchy v4.0.4 is already two Arch packages built from one tree, so the port is that tree on a branch of a fork, with pacman replaced by apt and the Arch-only parts removed, built into five Debian packages whose names, paths, commands and even the icon font's family are the distro's, through a rename that runs at build time. The proof is the QEMU test, which now boots into the ported session, lets the port's own first-run set the theme, and switches themes live.

## Terms

Each entry uses only terms defined above it, in the developer README's [Terms](README.md#terms), in the plan's [Terms](0%20-%20plan.md#terms), in the policy's [Terms](1%20-%20policy.md#terms) or in [step 5's](5%20-%20hyprland-quickshell.md#terms).

### The fork and the port branch

`santisbon/omarchy`, a fork of `omacom/omarchy`, with a branch `oaxaca` that starts at the pinned tag (`v4.0.4`) and holds every change the port makes as commits on top of it. The branch keeps Omarchy's names in every file (`omarchy-*`, `OMARCHY_PATH`, `/usr/share/omarchy`), so that a rebase onto the next Omarchy tag meets the same names on both sides. The local checkout is `~/Projects/omarchy`, with the remote `upstream` pointing at `omacom/omarchy`.

### The rename script

`port/rename.sh` on the port branch. Given a copy of the tree and the identity from `distro.conf` (`DISTRO_ID`, `DISTRO_NAME`), it deletes Omarchy's branded wallpapers, rewrites "omarchy", "Omarchy" and "OMARCHY" in every text file (leaving Omarchy's own addresses alone), renames every file and directory carrying the name, and renames the icon font's family inside the TTF with fontTools. The packaging runs it on a copy inside the build; it never runs on the checkout.

### Omarchy's two packages

How Omarchy ships itself since v4: `omarchy`, with the commands (`bin/`), the install scripts, the themes, the migrations and the shell; and `omarchy-settings`, with everything that must be on disk before a user is created: `/etc/skel`, `/etc` drop-ins, the systemd units, fonts, the SDDM and Plymouth themes and the branding. Their recipes (`pkgbuilds/omarchy/PKGBUILD` and `pkgbuilds/omarchy-settings/PKGBUILD` in `omacom/omarchy-pkgs`) are the file-for-file map this port follows. Omarchy's own `docs/file-layout.md` describes the same map in prose.

### Three layers of a user's home

Omarchy's model, kept by the port: `/etc/skel` seeds a new user's home at creation (`useradd -m` copies the tree); the first graphical login runs `<id>-provision-first-run`, which does what `/etc/skel` cannot (set the theme, enable the user units, show the welcome notification); and `<id>-reinstall-configs` is the explicit, destructive resync of an existing home to the shipped defaults.

### apply-system

`<id>-apply-system --install-user <user> --first-install`: the root-side setup script the installer runs on a new system after the packages are installed and the user exists. It sources `install/config/all.sh` (Chromium's first-run preferences, browser policy directories, the lock-screen PAM files, the services to enable), `install/hardware/all.sh` (vendor and device quirks), `install/login/all.sh` and `install/post-install/all.sh`, logging to `/var/log/<id>-install.log`. Omarchy's installation ISO (the Arch-based live image built by `omacom/omarchy-iso`, whose installer runs the script in the new system's chroot) calls it; here the boot test calls it from a oneshot unit before the display manager starts, and the installer (step 7) will call it the same way.

### Substitution variable

A `${name:Depends}`-style token in `debian/control` that `dpkg-gencontrol` replaces with a value from `debian/<package>.substvars`. The metapackage's dependency list is one: `${port:Depends}` is filled at build time from the package list in the ported tree.

### Component tarball

In a `3.0 (quilt)` source package, an additional upstream tarball `<source>_<version>.orig-<name>.tar.gz` that `dpkg-source` unpacks into the directory `<name>/` at the top of the tree. Used for a git submodule the release tarball lacks, and for the crates a Rust program needs to build without network.

## What the port changed in Omarchy's tree

The branch's diff against `v4.0.4`, by area. The authoritative list is `git diff --stat v4.0.4..oaxaca` in the fork.

- **Package management** (`bin/omarchy-pkg-*`, the update pipeline, versions): pacman and the AUR become apt. `omarchy-pkg-add/-missing/-present/-drop` use `apt-get` and `dpkg-query`; `omarchy-pkg-install/-remove` keep their fzf pickers (a picker here is a list in a terminal that the user narrows by typing and picks entries from, drawn by the fzf fuzzy finder) over `apt-cache pkgnames` and `apt-mark showmanual`, and four new pickers do the same for the two stores (`omarchy-pkg-snap-install/-remove`, `omarchy-pkg-flatpak-install/-remove`, choice 22); two new helpers, `omarchy-pkg-repo-add` and `-repo-remove`, write a vendor's keyring and deb822 sources file (and an optional pin), which the browser and service installers use. `omarchy-update` runs `apt-get update` and `full-upgrade`, then migrations, hooks, mise, orphans (`apt-get autoremove`), log analysis, status and restart; the snapshot, keyring, AUR and pacman-guard steps are gone. `omarchy-update-available` reads `apt list --upgradable` (the config package turns on apt's daily list refresh so that works without privileges). `omarchy-version` reads the tools package's version from dpkg.
- **System setup** (`install/`): the config scripts that edited Arch's PAM stacks, pacman, snapper and the powerprofilesctl shebang are gone; `enable-services.sh` enables what Ubuntu does not enable by itself and masks nothing; `firewall.sh` is gone: ufw stays exactly as Ubuntu ships it, installed with `ENABLED=no` in `/etc/ufw/ufw.conf` so that its unit loads no rule, and Ubuntu's own policies in `/etc/default/ufw` waiting for the user's `ufw enable` (choice 13); Omarchy's rules for LocalSend's port and Docker's DNS, its `ufw-docker` add-on and its enabling of the service are not applied; the hardware leaves that only installed Arch DKMS packages or wrote limine drop-ins are gone, so are the Apple F-key, iwd and networkd-wait-online ones (section "Ubuntu's configuration"), the ones that write modprobe or udev files for a detected device stay, and the Intel ones use `intel-lpmd`, `thermald` and `firmware-sof-signed`; the provisioning tree Omarchy's installation ISO used is gone; the per-user scripts no longer create Omarchy's passwordless keyring (the distro keeps Ubuntu's, step 4 choice 14) and skip mise and Chromium when absent.
- **PAM and security**: the lock screen's password stack names `pam_unix.so nullok` directly and takes its account check from Ubuntu's `common-account`; its fingerprint stack is `auth required pam_fprintd.so`. The fingerprint and FIDO2 setup scripts install nothing (the packages are dependencies of the desktop, policy decision of 2026-10-09) and edit no PAM file: they enable a `pam-auth-update` profile, Ubuntu's mechanism for the `common-*` stacks (`libpam-fprintd`'s own `fprintd` profile; a `oaxaca-u2f` profile shipped by `oaxaca-config`, since `libpam-u2f` has none), and the removal scripts disable it; `sshd` becomes `openssh-server` and `ssh.service`; every `%wheel` in `etc/sudoers.d/` becomes `%sudo`.
- **Files under `etc/` and `default/`**: limine, mkinitcpio, pacman, snapper, libalpm, the CUPS hardening, `nsswitch.conf`, `faillock.conf`, `plymouthd.conf`, SDDM's Wayland greeter file (the session package has its own) and the ASUS sleep hooks are gone; `fastfetch` lost its branch and channel lines; the tzupdate sudoers rule became `omarchy-timezone`.
- **Bindings and menu**: the bindings and menu entries for programs the distro cannot install (Omarchy's own apps: omacalc, herdr, cliamp, omawrite, voxtype; the AUR; channels; hibernation; the btrfs factory reset; direct boot; the ASUS hybrid-GPU toggle; the Nerd Font installers; the Omarchy Discord community) are gone. "Learn > Arch" became "Learn > Ubuntu". Setup > Monitors opens `nwg-displays`, writing `~/.config/hypr/monitors-gui.lua`, which the skel `monitors.lua` loads when it exists; editing the file is the second entry.
- **Third-party installers** (the section "The install catalogue" lists every entry and its source): browsers come from Mozilla's and Brave's apt sources and, for Chromium, the xtradeb PPA (choice 16); VSCodium, Sublime Text, 1Password, Signal, Spotify and Tailscale from their vendors' apt sources through `oaxaca-pkg-repo-add`; Chrome, Edge and VS Code were replaced on 2026-10-10 by Chromium, Brave Origin and VSCodium (the proprietary builds have open counterparts that the port's theme and policy scripts already supported); the rest as the section says.
- **Ubuntu names**: `imv` is `imv-wayland` on Ubuntu (`/usr/bin/imv` belongs to `renameutils` there), so the launcher and the Plymouth preview call that name.

## Choices

1. **A fork with a branch, renamed at build time, instead of a renamed copy in this repository.** The policy (section 3) asks for a fork that rebases onto Omarchy's tags; a tree that already carries the distro's name would conflict on every line of every rebase. Keeping Omarchy's names on the branch and renaming in the build keeps rebases to the real changes. The cost is a script that must stay complete (the test is the built packages: nothing in them says "omarchy" except Omarchy's own addresses). Rejected: a subtree or a snapshot copy (no rebase); compatibility symlinks (policy section 4 says why).
2. **One source, five binary packages, all at the tag's version.** Omarchy's two recipes are the map, and splitting `omarchy` into tools, shell and themes follows the plan's package list while keeping the tree's paths. The metapackage joins the same source because its dependency list is the ported package list from that tree; the policy's version table is corrected. Rejected: a native `oaxaca-desktop` with a hand-maintained list (two copies of one list drift).
3. **Chromium preinstalled, from the xtradeb PPA, installed by name rather than as a dependency (2026-10-14; until then, no browser).** Omarchy installs Chromium (`install/omarchy-base.packages` line 16 at v4.0.4), and its menu, web apps, theme switch and copy-URL extension assume a Chromium-family browser. Ubuntu's archive has no Chromium deb: `chromium` and `chromium-browser` are placeholders that install the snap. The first decision (2026-10-10) was no browser at all, because any Chromium deb means a source outside Ubuntu's archive on every install; that left a fresh install where web apps had nothing to open in (choice 18, c). Chosen now: the image (desktop and live profiles of `scripts/rootfs-create.sh`) carries `chromium` from the xtradeb PPA, the source the menu's Chromium entry already used (choice 16), with the same three apt files that entry writes, so Remove > Browser > Chromium and a reinstall from the menu work on the preinstalled copy unchanged. `chromium` is installed by name and not added to `oaxaca-desktop`'s Depends, so that removing it from the menu does not also remove the metapackage. An installed system that came from an older image does not get Chromium from `oaxaca-update`; Install > Browser > Chromium adds it. The PPA's launcher, `/usr/bin/chromium`, is Debian's: it reads flags from `/etc/chromium.d/*`, not from `~/.config/chromium-flags.conf` (an Arch wrapper feature, as the plan noted), so Omarchy's flags and its three bundled extensions never applied, even to the menu's Chromium; `oaxaca-config` now ships `/etc/chromium.d/zz-oaxaca-user-flags`, which reads that file. Rejected: Canonical's Chromium snap, checked on 2026-10-14 from `chromium_3554.snap` (155.0.8059.39, strict confinement). Its `meta/snap.yaml` grants only `/etc/chromium-browser/policies` (plug `etc-chromium-browser-policies`) and its launcher prefers `/var/snap/chromium/current/policies`, so the theme switch's `/etc/chromium/policies/managed/color.json` would never be read; the running browser is `$SNAP/usr/lib/chromium-browser/chrome`, so the switch's `pgrep -x chromium` refresh would miss it; and the default-browser entry, the web-app launcher, the copy-URL manifest under `~/.config/chromium` and the flags file all name paths a strict snap does not use. Also rejected: Chromium as a dependency of the metapackage (removal from the menu would take the metapackage with it); Mozilla's repository baked in for Firefox (Omarchy's browser is Chromium, and web apps need a Chromium-family browser).
4. **Migrations are not shipped.** They repair existing Omarchy installs for changes made before v4.0.4; a fresh Oaxaca user has nothing to migrate, and the Arch recipe marks them all done for new users anyway. `oaxaca-migrate` stays, finds nothing, and the mechanism is ready for the port's own migrations (roadmap step 8). Step 8 (2026-10-11) shipped the directory, deleted Omarchy's migrations on the branch, and runs the runner in its upgrade test; see [docs/8 - update-path.md](8%20-%20update-path.md). Rejected: shipping Omarchy's 106 migrations, most of which call pacman.
5. **Omarchy's own applications are not ported in this step.** `aether`, `cliamp`, `herdr`, `omacalc`, `omacut`, `omawrite`, `tensaku`, `tobi-try`, `ttfx`, `usage`, `voxtype`, `omarchy-nvim` are separate programs with their own recipes in `omarchy-pkgs`; each is a package of its own. Their bindings and menu entries are removed so that nothing on screen fails. Carried.
6. **Install-time setup stays a script the installer runs, not a postinst.** Writing the lock-screen PAM files, enabling services and applying a detected device's quirk change the system's behaviour; a package's postinst that did that on every install and upgrade would surprise anyone installing the desktop on an existing machine. `oaxaca-apply-system` runs once, when the installer says so, and the boot test runs it the same way. Rejected: doing it in `oaxaca-config.postinst`.
7. **Branding placeholders, generated.** The name in a box as text art and as a rendered PNG, from `distro.conf`, so a rebrand needs no artwork change; the wallpapers that carried Omarchy's mark are deleted by the rename script. The icon font keeps Omarchy's mark at U+E900 until a glyph exists. Flagged for the user.
8. **The desktop metapackage's list is Omarchy's list under Ubuntu names, with drops recorded in the file.** Every drop is a comment at the end of `install/oaxaca-base.packages` with the reason: not in Ubuntu (`pinta`, `localsend`, `obsidian`, `moonlight-qt`, `lazydocker`, `tzupdate`, `ufw-docker`), Arch-only (`expac`, `fakeroot`, `pacman-contrib`, `yay`, `kernel-modules-hook`), Omarchy's own, or carried by another package of ours. `build-essential` stands in for `clang` and `llvm`.
9. **`fd` and `bat` by symlink.** Ubuntu ships `fdfind` and `batcat`; the scripts and the aliases say `fd` and `bat`. Two symlinks in `oaxaca-tools` with `Conflicts: fdclone` (the one package in `stonking` that owns `/usr/bin/fd`). Rejected: rewriting every call (the user types the short names too).
10. **Two packages added to Omarchy's list for Ubuntu: `upower` and `systemd-oomd`.** The shell's power panel reads UPower through Quickshell, and on Arch `quickshell` depends on `upower`; Ubuntu's does not, and the first boot test showed the panel failing to load. `systemd-oomd` is part of Arch's systemd and a separate package on Ubuntu, and `enable-services.sh` enables it. Both are recorded in the list with the reason.
11. **`oaxaca-shell` depends on the Qt QML modules the shell imports, not only on `quickshell`.** The shell's files import `QtQuick` with `Controls`, `Layouts`, `Shapes`, `Effects` and `Window`, and `QtQml.Models`. Ubuntu's `quickshell` depends on the first three only; the second boot test showed the background, the lock screen, the tray and the image picker failing with `module "QtQuick.Effects" is not installed`. The seven `qml6-module-*` packages are listed explicitly, each mapped from the module's `qmldir` path in the archive's `Contents` index. Rejected: depending on `qml6-module-qtquick-effects` alone (the next import would fail the same way).
12. **nwg-displays writes to a `.conf` name.** Its `-m` option keeps Lua output at a custom path only when the value ends in `.conf` (the Lua path swaps the suffix); the menu entry passes `~/.config/hypr/monitors-gui.conf`, which yields `monitors-gui.lua`, and the skel `monitors.lua` loads that module when it exists.
13. **ufw as Ubuntu ships it, with no rules from Omarchy.** ufw is Ubuntu's default firewall configuration tool (Ubuntu's server documentation, "Firewalls": "The default firewall configuration tool for Ubuntu is `ufw`" and "`ufw` by default is initially disabled"), and `install/omarchy-base.packages` keeps the package because Ubuntu installs it. Omarchy's `install/config/firewall.sh` enabled the service and added its own rules (deny incoming, allow outgoing, LocalSend's port 53317, Docker's DNS from two private ranges) plus the `ufw-docker` add-on; that script and its test are deleted from the port branch, `install/config/all.sh` no longer calls it, and the acceptance test no longer expects `ufw.service` enabled. The installed system therefore has what a fresh Ubuntu install has: the `ufw` package's postinst enables `ufw.service`, that unit runs `/usr/lib/ufw/ufw-init start quiet`, and with `ENABLED=no` in `/etc/ufw/ufw.conf` that script exits without loading any rule, so `systemctl is-enabled ufw` says `enabled` while `ufw status` says inactive; the policies in `/etc/default/ufw` (incoming `DROP`, outgoing `ACCEPT`, forward `DROP`) are Ubuntu's and only apply once a user runs `ufw enable`. The boot test reports this state as `ufw: enabled ENABLED=no`, the same two values this workstation's stock Ubuntu shows. The one ufw command left in the port is in `oaxaca-setup-security-sshd`, which adds a rate-limited rule for port 22 when the user chooses to set up SSH from the menu; that is the user configuring their own firewall with Ubuntu's tool, and it only takes effect if the user also enables ufw. Rejected: Omarchy's rules (a firewall on by default with product-specific holes is Omarchy's policy, not Ubuntu's, and `ufw-docker` has no Ubuntu package). Carried: Omarchy's manual pages under `manual/` (22, 35, 48) still describe a firewall that is on by default; the manual is not shipped by any package.
14. **Ubuntu's configuration for every Ubuntu component, Omarchy's only with a reason.** The section "Ubuntu's configuration, not Omarchy's" is the list. The deciding facts are stonking's own packages, read from their `.deb` files; the first inventory compared against this workstation's Kubuntu 26.04 and had eight claims wrong (plocate's power condition, which package owns `/etc/sudoers`, how unattended-upgrades reaches a desktop, the keyserver default, zram-generator's shipped config, `localsearch`'s inotify value, SDDM's vendor config, Plymouth's theme selection), which is why the rule names the series. Rejected: keeping Omarchy's tunings because they are harmless (each one is a value a user of an Ubuntu-based system would not expect, and together they are a second set of defaults to document and to re-check at every rebase).
15. **A core desktop package and an optional apps package, nothing of Omarchy's taste.** The section "Core and apps" is the list and the evidence. Rejected: shipping Omarchy's list whole with its own "remove preinstalls" menu entry (the user would start from the bloated state and dig out); a large apps package carrying LibreOffice, Kdenlive and the rest as an opt-in (they are Omarchy's choices, not a desktop's needs, and anyone who wants them has apt).
16. **Chromium from the xtradeb PPA, pinned below Ubuntu's archive.** Ubuntu's `chromium-browser` is a placeholder that installs the snap, the Chromium project publishes no apt repository, and Debian's package is built for Debian's libraries. The xtradeb PPA (`launchpad.net/~xtradeb/+archive/ubuntu/apps`, "Unofficial Ubuntu application packages maintained by xtradeb") builds upstream Chromium for each Ubuntu series, `stonking` included (154.0.8037.92-1xtradeb1.2610.1 on 2026-10-10, amd64 and arm64), so apt keeps the browser current. Remove > Snap lists the snaps snapd's local API (`GET /v2/snaps` on `/run/snapd.socket`, readable without sudo) reports with type `app` and at least one command, so bases (`core24`), snapd and content snaps that only serve other snaps (`gtk-common-themes`, `gnome-46-2404`) stay out of the list. Rejected: one picker over both stores (each store names, installs and confines apps differently, and the Notes and confinement questions are the Snap Store's alone); a GUI store app (Ubuntu's App Center is itself a snap, and the menu's Package entry already set the pattern of a terminal picker); filtering Remove > Snap by `snap list`'s Notes column (it marks bases and snapd but not content snaps).
21. **The menu's package tests ask dpkg, as the real helpers do (2026-10-14).** The shell's menu (`shell/plugins/menu/MenuModel.js`) answers every entry's `when:` test in one bash process and, for speed, defines its own `omarchy-pkg-present` and `omarchy-pkg-missing` for that process from one listing of installed packages. Upstream built the listing from `pacman -Qq` and `pacman -Qi`; the port had moved `bin/omarchy-pkg-present` and `-missing` to `dpkg-query` but not this copy, so on Oaxaca the listing was empty: every Install entry guarded by `! omarchy-pkg-present` showed with its package installed (Install > Browser > Chromium beside an installed Chromium, reported from the laptop) and every Remove entry was hidden. The copy now lists every instance dpkg knows (`dpkg-query -W -f='${db:Status-Status}\t${Package}\n' '*'`) and keeps a name that appears once and is installed, which is exactly when the real helpers' `${db:Status-Status}` string reads "installed" (a name known in two architectures concatenates two statuses and never does); a name with an architecture or a character no package name has goes to `dpkg-query` itself. On 2026-10-14 the copy and the real helpers gave the same answer in 22 comparisons against this workstation's dpkg database (a package known in two architectures, one left as configuration files, a version constraint, the empty argument), and building the listing took 38 ms. The fork's `test/shell.d/menu-guards-test.sh` had caught the mismatch all along (`omarchy-pkg-present sh: real=1 shadowed=0`) but nothing runs the fork's tests; its package section now stubs `dpkg-query` instead of `pacman` and passes, and fails when the copy is broken on purpose. The rest of the fork's shell suite (`test/shell`) had 62 failures before and after this change, upstream tests for what the port replaced (carried below).

Without `UPSTREAM_DIR`, `build.sh` clones the fork named in `distro.conf` and builds the ref `OMARCHY_PORT_REF` (the `oaxaca` branch today; a tag once a release is cut), after checking that the fetched commit's date, count of commits since `OMARCHY_TAG` and 8-digit hash are the `OMARCHY_PORT_DATE`, `OMARCHY_PORT_COUNT` and `OMARCHY_PORT_COMMIT` in `distro.conf` (policy, version scheme). When the fork has moved on, the build stops and prints the three values to put there.
