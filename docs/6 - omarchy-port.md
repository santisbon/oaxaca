# 6. The Omarchy port

Roadmap step 6 of the [plan](0%20-%20plan.md#roadmap-option-b): "port Omarchy into packages (fork omacom/omarchy; MIT, keep the license)". Done 2026-10-10. The answer in one line: Omarchy is already two Arch packages built from one tree, so the port is that tree on a branch of a fork, with pacman replaced by apt and the Arch-only parts removed, built into five Debian packages whose names, paths, commands and even the icon font's family are the distro's, through a rename that runs at build time. The proof is the QEMU test, which now boots into the ported session, lets the port's own first-run set the theme, and switches themes live.

## Terms

Each entry uses only terms defined above it, in the developer README's [Terms](README.md#terms), in the plan's [Terms](0%20-%20plan.md#terms), in the policy's [Terms](1%20-%20policy.md#terms) or in [step 5's](5%20-%20hyprland-quickshell.md#terms).

### The fork and the port branch

`santisbon/omarchy`, a fork of `omacom/omarchy`, with a branch `oaxaca` that follows the tag named as `OMARCHY_TAG` in `distro.conf` (`v4.0.6`) and holds every change the port makes as commits of its own; each new Omarchy tag is merged into the branch (policy section 3, choice 101). The branch keeps Omarchy's names in every file (`omarchy-*`, `OMARCHY_PATH`, `/usr/share/omarchy`), so that a merge of the next Omarchy tag meets the same names on both sides. A checkout of the fork adds `omacom/omarchy` as the remote `upstream`.

### The rename script

`port/rename.sh` on the port branch. Given a copy of the tree and the identity from `distro.conf` (`DISTRO_ID`, `DISTRO_NAME`), it deletes Omarchy's branded wallpapers, rewrites "omarchy", "Omarchy" and "OMARCHY" in every text file (leaving Omarchy's own addresses alone, and, since choice 86, the names plugins and themes written for Omarchy use and users do not see), renames every file and directory carrying the name, and fails when any "omarchy" is left outside those two lists. Until choice 86 it also renamed the icon font's family inside the TTF with fontTools. The packaging runs it on a copy inside the build; it never runs on the checkout.

### Omarchy's two packages

How Omarchy ships itself since v4: `omarchy`, with the commands (`bin/`), the install scripts, the themes, the migrations and the shell; and `omarchy-settings`, with everything that must be on disk before a user is created: `/etc/skel`, `/etc` drop-ins, the systemd units, fonts, the SDDM and Plymouth themes and the branding. Their recipes (`pkgbuilds/omarchy/PKGBUILD` and `pkgbuilds/omarchy-settings/PKGBUILD` in `omacom/omarchy-pkgs`) are the file-for-file map this port follows. Omarchy's own `docs/file-layout.md` describes the same map in prose.

### Three layers of a user's home

Omarchy's model, kept by the port: `/etc/skel` seeds a new user's home at creation (`useradd -m` copies the tree); the first graphical login runs `<id>-provision-first-run`, which does what `/etc/skel` cannot (set the theme, enable the user units, show the welcome notification); and `<id>-reinstall-configs` is the explicit, destructive resync of an existing home to the shipped defaults.

### apply-system

`<id>-apply-system --install-user <user> --first-install`: the root-side setup script the installer runs on a new system after the packages are installed and the user exists. It sources `install/config/all.sh` (Chromium's first-run preferences, browser policy directories, the lock-screen PAM files, the services to enable), `install/hardware/all.sh` (vendor and device quirks), `install/login/all.sh` and `install/post-install/all.sh`, logging to `/var/log/<id>-install.log`. Omarchy's installation ISO (the Arch-based live image built by `omacom/omarchy-iso`, whose installer runs the script in the new system's chroot) calls it; here the boot test calls it from a oneshot unit before the display manager starts, and the installer (step 7) will call it the same way.

### Substitution variable

A `${name:Depends}`-style token in `debian/control` that `dpkg-gencontrol` replaces with a value from `debian/<package>.substvars`. The metapackage's dependency list is one: `${port:Depends}` is filled at build time from the package list in the ported tree.

### Component tarball

In a `3.0 (quilt)` source package, an additional upstream tarball `<source>_<version>.orig-<name>.tar.gz` that `dpkg-source` unpacks into the directory `<name>/` at the top of the tree. Used for a git submodule the release tarball lacks, and for the crates a Rust program needs to build without network.

### SSH client and SSH server

OpenSSH's two halves. The SSH client is the `ssh` command (Ubuntu's `openssh-client`, in every Oaxaca system), run on the computer you type at. The SSH server is `sshd` (Ubuntu's `openssh-server`), run on the computer you connect to; an Oaxaca system has none until Setup > Security > SSHD installs it. `ssh <user>@<host> <command>` connects the client to the server on `<host>`, logs in as `<user>`, runs `<command>` there and shows its output; without `<command>` it opens an interactive shell there instead.

### Placeholder

A part of a command written in angle brackets, such as `<user>` or `<host>`, that you replace, brackets included, with your own value before running the command. Each placeholder is explained next to the command that uses it. Everything outside angle brackets is typed as shown.

## What the port changed in Omarchy's tree

The branch's diff against `v4.0.6`, by area. The authoritative list is `git diff --stat v4.0.6 oaxaca` in the fork.

- **Package management** (`bin/omarchy-pkg-*`, the update pipeline, versions): pacman and the AUR become apt. `omarchy-pkg-add/-missing/-present/-drop` use `apt-get` and `dpkg-query`; `omarchy-pkg-install/-remove` keep their fzf pickers (a picker here is a list in a terminal that the user narrows by typing and picks entries from, drawn by the fzf fuzzy finder) over `apt-cache pkgnames` and `apt-mark showmanual`, and four new pickers do the same for the two stores (`omarchy-pkg-snap-install/-remove`, `omarchy-pkg-flatpak-install/-remove`, choice 22); two new helpers, `omarchy-pkg-repo-add` and `-repo-remove`, write a vendor's keyring and deb822 sources file (and an optional pin), which the browser and service installers use. `omarchy-update` runs `apt-get update` and `full-upgrade`, then migrations, hooks, mise, orphans (`apt-get autoremove`), log analysis, status and restart; the keyring, AUR and pacman-guard steps are gone, and the snapshot step, gone at first, came back with Timeshift on btrfs installs (choice 38). `omarchy-update-available` reads `apt list --upgradable` (the config package turns on apt's daily list refresh so that works without privileges). `omarchy-version` reads the tools package's version from dpkg.
- **System setup** (`install/`): the config scripts that edited Arch's PAM stacks, pacman, snapper and the powerprofilesctl shebang are gone; `enable-services.sh` enables what Ubuntu does not enable by itself and masks nothing; `firewall.sh` was deleted (choice 13) and rewritten for Ubuntu (choice 40): it allows LocalSend's port and turns ufw on for the next boot, on Ubuntu's own policies in `/etc/default/ufw`, without Omarchy's Docker rules or its `ufw-docker` add-on; the hardware leaves that only installed Arch DKMS packages or wrote limine drop-ins are gone, so are the Apple F-key, iwd and networkd-wait-online ones (section "Ubuntu's configuration"), the ones that write modprobe or udev files for a detected device stay, and the Intel ones use `intel-lpmd`, `thermald` and `firmware-sof-signed`; the provisioning tree Omarchy's installation ISO used is gone; the per-user scripts no longer create Omarchy's passwordless keyring (the distro keeps Ubuntu's, step 4 choice 14) and skip mise and Chromium when absent.
- **PAM and security**: the lock screen's password stack names `pam_unix.so nullok` directly and takes its account check from Ubuntu's `common-account`; its fingerprint stack is `auth required pam_fprintd.so`. The fingerprint and FIDO2 setup scripts install nothing (the packages are dependencies of the desktop, policy decision of 2026-10-09) and edit no PAM file: they enable a `pam-auth-update` profile, Ubuntu's mechanism for the `common-*` stacks (since 2026-10-16 an `oaxaca-fprintd` profile shipped by `oaxaca-config`, `libpam-fprintd`'s `fprintd` line with the lid-closed gate in front, choice 53; a `oaxaca-u2f` profile shipped by `oaxaca-config`, since `libpam-u2f` has none; both start with a gate that limits them to `sudo`, `sudo -i` and polkit, so the login screen keeps the password, choice 103), and the removal scripts disable it; `sshd` becomes `openssh-server` and `ssh.service`; every `%wheel` in `etc/sudoers.d/` becomes `%sudo`.
- **Files under `etc/` and `default/`**: limine, mkinitcpio, pacman, snapper, libalpm, the CUPS hardening, `nsswitch.conf`, `faillock.conf`, `plymouthd.conf`, SDDM's Wayland greeter file (the session package has its own) and the ASUS sleep hooks are gone; `fastfetch` lost its branch and channel lines; the tzupdate sudoers rule became `omarchy-timezone`.
- **Bindings and menu**: the bindings and menu entries for programs the distro cannot install (Omarchy's own apps: omacalc, herdr, cliamp, omawrite, voxtype; the AUR; channels; hibernation; the btrfs factory reset; direct boot; the ASUS hybrid-GPU toggle; the Nerd Font installers; the Omarchy Discord community) are gone. "Learn > Arch" became "Learn > Ubuntu". Setup > Monitors opens `nwg-displays`, writing `~/.config/hypr/monitors-gui.lua`, which the skel `monitors.lua` loads when it exists; editing the file is the second entry.
- **Third-party installers** (the section "The install catalogue" lists every entry and its source): browsers come from Google's (Chrome), Mozilla's and Brave's apt sources and, for Chromium, the xtradeb PPA (choice 16); VS Code, Sublime Text, 1Password, Signal, Spotify, Mullvad VPN and Tailscale from their vendors' apt sources through `oaxaca-pkg-repo-add`, and VSCodium from Flathub (choice 17). On 2026-10-10 Chrome, Edge and VS Code were first replaced by Chromium, Brave Origin and VSCodium; Chrome came back the same day as a second browser entry (choice 16) and VS Code next to VSCodium (choice 17), while Edge stays out (choice 74); the rest as the section says.
- **Ubuntu names**: `imv` is `imv-wayland` on Ubuntu (`/usr/bin/imv` belongs to `renameutils` there), so the launcher and the Plymouth preview call that name.

## Choices

Rule, set 2026-10-16: the port is built up the way the Ubuntu base is (policy, section 3, "Build up, never strip"). Nothing of Omarchy's is shipped and then removed or turned off; the port starts from Ubuntu's configuration plus the parts of Omarchy the desktop needs to run (sections "Ubuntu's configuration, not Omarchy's" and "Core and apps"), and each further Omarchy feature is added by a choice below that gives the reason.

An audit on 2026-10-16 checked every removal described in this document against its reason; the fork's [PORT-REMOVALS.md](https://github.com/santisbon/omarchy/blob/oaxaca/PORT-REMOVALS.md), next to `PORT.md`, lists what the port still lacks with a verdict for each, the candidates still to restore, and, at its end, everything restored since with the choice that records it. Restoring an item is an addition under the rule above, recorded as a choice here.

1. **A fork with a branch, renamed at build time, instead of a renamed copy in this repository.** The policy (section 3) asks for a fork that merges Omarchy's tags; a tree that already carries the distro's name would conflict on every line of every merge. Keeping Omarchy's names on the branch and renaming in the build keeps merges to the real changes. The cost is a script that must stay complete (the test is the built packages: nothing in them says "omarchy" except Omarchy's own addresses). Rejected: a subtree or a snapshot copy (no merge); compatibility symlinks (policy section 4 says why).
2. **One source, five binary packages, all at the tag's version.** Omarchy's two recipes are the map, and splitting `omarchy` into tools, shell and themes follows the plan's package list while keeping the tree's paths. The metapackage joins the same source because its dependency list is the ported package list from that tree; the policy's version table is corrected. Rejected: a native `oaxaca-desktop` with a hand-maintained list (two copies of one list drift).
3. **Chromium preinstalled, from the xtradeb PPA, installed by name rather than as a dependency (2026-10-14; until then, no browser).** Omarchy installs Chromium (`install/omarchy-base.packages` line 16 at v4.0.4), and its menu, web apps, theme switch and copy-URL extension assume a Chromium-family browser. Ubuntu's archive has no Chromium deb: `chromium` and `chromium-browser` are placeholders that install the snap. The first decision (2026-10-10) was no browser at all, because any Chromium deb means a source outside Ubuntu's archive on every install; that left a fresh install where web apps had nothing to open in (choice 18, c). Chosen now: the image (desktop and live profiles of `scripts/rootfs-create.sh`) carries `chromium` from the xtradeb PPA, the source the menu's Chromium entry already used (choice 16), with the same three apt files that entry writes, so Remove > Browser > Chromium and a reinstall from the menu work on the preinstalled copy unchanged. `chromium` is installed by name and not added to `oaxaca-desktop`'s Depends, so that removing it from the menu does not also remove the metapackage. An installed system that came from an older image does not get Chromium from `oaxaca-update`; Install > Browser > Chromium adds it. The PPA's launcher, `/usr/bin/chromium`, is Debian's: it reads flags from `/etc/chromium.d/*`, not from `~/.config/chromium-flags.conf` (an Arch wrapper feature, as the plan noted), so Omarchy's flags and its three bundled extensions never applied, even to the menu's Chromium; `oaxaca-config` now ships `/etc/chromium.d/zz-oaxaca-user-flags`, which reads that file. Rejected: Canonical's Chromium snap, checked on 2026-10-14 from `chromium_3554.snap` (155.0.8059.39, strict confinement). Its `meta/snap.yaml` grants only `/etc/chromium-browser/policies` (plug `etc-chromium-browser-policies`) and its launcher prefers `/var/snap/chromium/current/policies`, so the theme switch's `/etc/chromium/policies/managed/color.json` would never be read; the running browser is `$SNAP/usr/lib/chromium-browser/chrome`, so the switch's `pgrep -x chromium` refresh would miss it; and the default-browser entry, the web-app launcher, the copy-URL manifest under `~/.config/chromium` and the flags file all name paths a strict snap does not use. Also rejected: Chromium as a dependency of the metapackage (removal from the menu would take the metapackage with it); Mozilla's repository baked in for Firefox (Omarchy's browser is Chromium, and web apps need a Chromium-family browser).
4. **Migrations are not shipped.** They repair existing Omarchy installs for changes made before v4.0.4; a fresh Oaxaca user has nothing to migrate, and the Arch recipe marks them all done for new users anyway. `oaxaca-migrate` stays, finds nothing, and the mechanism is ready for the port's own migrations (roadmap step 8). Step 8 (2026-10-11) shipped the directory, deleted Omarchy's migrations on the branch, and runs the runner in its upgrade test; see [docs/8 - update-path.md](8%20-%20update-path.md). Rejected: shipping Omarchy's 106 migrations, most of which call pacman.
5. **Omarchy's own applications are not ported in this step.** `aether`, `cliamp`, `herdr`, `omacalc`, `omacut`, `omawrite`, `tensaku`, `tobi-try`, `ttfx`, `usage`, `voxtype`, `omarchy-nvim` are separate programs with their own recipes in `omarchy-pkgs`; each is a package of its own. Their bindings and menu entries are removed so that nothing on screen fails. Carried.
6. **Install-time setup stays a script the installer runs, not a postinst.** Writing the lock-screen PAM files, enabling services and applying a detected device's quirk change the system's behaviour; a package's postinst that did that on every install and upgrade would surprise anyone installing the desktop on an existing machine. `oaxaca-apply-system` runs once, when the installer says so, and the boot test runs it the same way. Rejected: doing it in `oaxaca-config.postinst`.
7. **Branding placeholders, generated.** *Replaced by choice 104 (2026-10-23): the distro has artwork.* The name in a box as text art and as a rendered PNG, from `distro.conf`, so a rebrand needs no artwork change; the wallpapers that carried Omarchy's mark are deleted by the rename script. The icon font keeps Omarchy's mark at U+E900 until a glyph exists. Flagged for the user.
8. **The desktop metapackage's list is Omarchy's list under Ubuntu names, with drops recorded in the file.** Every drop is a comment at the end of `install/oaxaca-base.packages` with the reason: not in Ubuntu (`pinta`, `localsend`, `obsidian`, `moonlight-qt`, `lazydocker`, `tzupdate`, `ufw-docker`), Arch-only (`expac`, `fakeroot`, `pacman-contrib`, `yay`, `kernel-modules-hook`), Omarchy's own, or carried by another package of ours. `build-essential` stands in for `clang` and `llvm`.
9. **`fd` and `bat` by symlink.** Ubuntu ships `fdfind` and `batcat`; the scripts and the aliases say `fd` and `bat`. Two symlinks in `oaxaca-tools` with `Conflicts: fdclone` (the one package in `stonking` that owns `/usr/bin/fd`). Rejected: rewriting every call (the user types the short names too).
10. **Two packages added to Omarchy's list for Ubuntu: `upower` and `systemd-oomd`.** The shell's power panel reads UPower through Quickshell, and on Arch `quickshell` depends on `upower`; Ubuntu's does not, and the first boot test showed the panel failing to load. `systemd-oomd` is part of Arch's systemd and a separate package on Ubuntu, and `enable-services.sh` enables it. Both are recorded in the list with the reason.
11. **`oaxaca-shell` depends on the Qt QML modules the shell imports, not only on `quickshell`.** The shell's files import `QtQuick` with `Controls`, `Layouts`, `Shapes`, `Effects` and `Window`, and `QtQml.Models`. Ubuntu's `quickshell` depends on the first three only; the second boot test showed the background, the lock screen, the tray and the image picker failing with `module "QtQuick.Effects" is not installed`. The seven `qml6-module-*` packages are listed explicitly, each mapped from the module's `qmldir` path in the archive's `Contents` index. Rejected: depending on `qml6-module-qtquick-effects` alone (the next import would fail the same way).
12. **nwg-displays writes to a `.conf` name.** Its `-m` option keeps Lua output at a custom path only when the value ends in `.conf` (the Lua path swaps the suffix); the menu entry passes `~/.config/hypr/monitors-gui.conf`, which yields `monitors-gui.lua`, and the skel `monitors.lua` loads that module when it exists.
13. **ufw as Ubuntu ships it, with no rules from Omarchy.** ufw is Ubuntu's default firewall configuration tool (Ubuntu's server documentation, "Firewalls": "The default firewall configuration tool for Ubuntu is `ufw`" and "`ufw` by default is initially disabled"), and `install/omarchy-base.packages` keeps the package because Ubuntu installs it. Omarchy's `install/config/firewall.sh` enabled the service and added its own rules (deny incoming, allow outgoing, LocalSend's port 53317, Docker's DNS from two private ranges) plus the `ufw-docker` add-on; that script and its test are deleted from the port branch, `install/config/all.sh` no longer calls it, and the acceptance test no longer expects `ufw.service` enabled. ## SSH commands into an installed system

Choice 91 gives a command run over SSH the tools installed through mise. This section shows how to run such a command and check the result. Each step says which computer the step runs on: **the Oaxaca machine**, the computer with Oaxaca installed, which runs the [SSH server](#ssh-client-and-ssh-server); or **the other computer**, any computer you connect from, which runs the [SSH client](#ssh-client-and-ssh-server). Parts in angle brackets are [placeholders](#placeholder).

### Set up the SSH server (the Oaxaca machine)

Press Super+Space and choose Setup > Security > SSHD. The entry opens a terminal running `oaxaca-setup-security-sshd`, a script that installs `openssh-server`, starts `ssh.service`, opens the SSH port in the firewall (`ufw limit 22/tcp`, which allows the port but refuses an address that tries too often), and asks for the SSH public key of the other computer, either fetched from a GitHub account (`https://github.com/<github user>.keys`, where `<github user>` is the account's name, which the script asks for) or pasted in. Once a key is authorized, the entry turns password logins off (`/etc/ssh/sshd_config.d/10-oaxaca-hardening.conf`), so from then on only a computer holding the matching private key can connect.

The two values the other computer needs come from the Oaxaca machine:

```
hostnamectl hostname
whoami
```

`hostnamectl hostname` prints the Oaxaca machine's host name, the one the installer's Users page proposed or you typed there (on the Legion laptop, the user name followed by `-83f5`). `whoami` prints your user name on the Oaxaca machine, the account the installer created.

### Run a command over SSH (the other computer)

```
ssh <user>@<host>.local '<command>'
```

- `<user>`: your user name on the Oaxaca machine, as `whoami` printed the name. When your user name on the other computer is the same, `<user>@` can be left out.
- `<host>`: the Oaxaca machine's host name, as `hostnamectl hostname` printed the name. The `.local` after the host name is typed as shown: the Oaxaca machine's Avahi daemon answers that name on the local network, for a computer whose name lookup asks for `.local` names (Ubuntu with `libnss-mdns`, as Oaxaca itself has it). A computer that cannot look up `.local` names uses the Oaxaca machine's network address in place of `<host>.local`; `hostname -I`, run on the Oaxaca machine, prints the address.
- `<command>`: what to run on the Oaxaca machine. The single quotes are typed as shown: they keep the other computer's shell from expanding `$` variables or `~` before the command reaches the Oaxaca machine.

On the Legion laptop, run from another computer on the same network, a command that asks the Oaxaca system where herdr is (installed through mise, choice 80) reads:

```
ssh <user>@<host>.local 'command -v herdr'
```

With choice 91 in place the command prints `/home/<user>/.local/share/mise/shims/herdr`; without choice 91 the command prints nothing, and ssh exits with status 1. A program that draws on the whole terminal, as herdr itself does, needs `ssh -t` in place of `ssh`, which gives the command a terminal on the Oaxaca machine.

### Check the PATH an SSH command gets (the other computer)

```
ssh <user>@<host>.local 'echo $PATH'
```

The printed PATH is the one the Oaxaca machine gives commands run over SSH. With choice 91 in place the PATH is Ubuntu's PATH followed by mise's shims and `~/.local/bin`, with `<user>`'s home directory written out:

```
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin:/home/<user>/.local/share/mise/shims:/home/<user>/.local/bin
```

The same check works on the Oaxaca machine alone, connecting to itself, with `localhost` in place of `<host>.local` (`ssh localhost 'echo $PATH'`), but only when the Oaxaca machine's own public key, `~/.ssh/id_ed25519.pub` after `ssh-keygen -t ed25519`, is among the keys Setup > Security > SSHD authorized, since password logins are off. The Legion laptop's Kubuntu and Oaxaca share one machine and never run at the same time, so Kubuntu cannot be the other computer for that machine's Oaxaca.
